# Card kinds — legacy / added / speculative

## Context

The asimov tech tree's data is currently a single TSV ([static/asimov.tsv](static/asimov.tsv), 1477 rows) exported from a Google Sheet ("[spreadsheet-new]" linked from the README). Both the runtime ([utils.js#L99](static/utils.js#L99) `loadGraph`) and the build script ([scripts/generate-site.py#L33](scripts/generate-site.py#L33) `load_inventions`) read that one TSV. The deploy flow is `deploy.sh` → `generate-site.py` → `rsync static/`.

Now the corpus is going to grow beyond Asimov's original list. Some entries fill gaps (a "couched lance" between stirrup and knight; "cannon-boring" between cannon and steam engine; ARPANET, the personal computer, the web). Some run *past* Asimov's late-20th-century horizon. And some are deliberately speculative — gestures at the future. The reader needs to see at a glance how speculative each card is, and the author needs **one editing surface, one ground-truth file**.

This plan adds:

1. A `Kind` column on every row — `legacy`, `added`, or `speculative`.
2. An automated fetch script so the repo TSV stays in sync with the sheet without download-and-paste.
3. Subtle visual differentiation per kind on the rendered cards.
4. A layout tweak so the initial camera fit isn't dominated by the speculative-future tail.

---

## Decisions locked in (from clarifying questions)

- **Ground truth**: same Google Sheet, with **one tab per slice** of the corpus. A single `Kind` column carries the full taxonomy: `legacy`, `added`, or `scenario-<slug>` for any speculative tab (e.g. `scenario-fusion`, `scenario-agi-dominant`, `scenario-climate-constrained`). Each `scenario-…` value is its own "cone of possibilities" — adding a new scenario = creating a new tab + adding one line to the fetch script's config. Kind is inferred per tab; the sheet has no Kind column of its own.
- **Pipeline**: an automated fetch script pulls each configured tab, tags each row with the kind from the tab config, and writes the merged result to `static/asimov.tsv` with an injected `Kind` column. The runtime reads a single TSV.

"Is this card speculative?" is a derived predicate (`kind.startsWith("scenario-")`), not a separate field — keeps the data model flat.

## Sheet-side setup (one-time, manual)

In the existing sheet ([1hDNXas7DzwglB95HV2_2u1utWAwBZR2hQHlMPz-fj5A](https://docs.google.com/spreadsheets/d/1hDNXas7DzwglB95HV2_2u1utWAwBZR2hQHlMPz-fj5A/edit?gid=0#gid=0)):

1. Keep the current tab named **`Asimov Prehistory to 1993`** as-is — it stays the legacy corpus.
2. Create one new tab for verified additions, e.g. **`Boris additions`** (gap-fillers and post-1993 entries that actually happened).
3. Create **one tab per future scenario** you want to author. Name them descriptively; the fetch script's config maps each tab name to a kind value. To start, e.g.: **`Speculative: AGI-dominant`** → `scenario-agi-dominant`, **`Speculative: Fusion economy`** → `scenario-fusion`. New scenarios = new tabs added later.
4. Copy the header row from the legacy tab into each new tab so columns line up (`ID, Year, Title, Description, Inventor, Location, Dependencies, Field, URL`).
5. Confirm the sheet is "Anyone with the link → Viewer" so the export URLs are anonymous-readable. (The README already links it publicly, so almost certainly already true.)

No Kind column is added in the sheet — the fetch script's tab config is the only place where "this tab means this kind" is encoded. To rename a tab, edit one line; to add a scenario, add one line.

## Data shape — `Kind` column (injected by the fetch script)

The sheet has no Kind column. The fetch script appends one when merging, so the resulting `static/asimov.tsv` looks like:

```
ID                 Year       Title  …  Field    URL    Kind
fire               500000 BCE …             Energy           legacy
couched-lance      1100       …             War    …         added
agi-foom           2032       …             Science …        scenario-agi-dominant
commercial-fusion  2055       …             Energy …         scenario-fusion
```

Allowed `Kind` values: `legacy`, `added`, or any `scenario-<slug>` (slug = lowercase-with-dashes). The runtime defaults `Kind = legacy` for empty/missing values — forgiving for hand-edits. Unknown non-scenario kinds get a single `console.warn` and fall back to `legacy`.

The same invention ID can appear in **at most one tab** (no cross-scenario aliasing in v1). Two scenarios that both want to assert "fusion-grid happens" should use distinct IDs (`fusion-grid-agi`, `fusion-grid-fusion`) or share a single `added` row if the prediction is scenario-independent.

`node.kind` becomes a runtime field alongside `node.id, node.year, node.deps, …`. It's read by:
- `card.js` / `world.js` → renders the `kind-…` class
- `world.js` `bbox` (optional flag)
- `utils.js` `validateData` (optional check)
- Future stories code (which already accepts any IDs from the merged corpus — no changes needed)

## The fetch script

[scripts/fetch-tsv.py](scripts/fetch-tsv.py) — minimal, no extra dependencies beyond `urllib`:

```python
#!/usr/bin/env python3
"""Pull the asimov inventions sheet (one tab per kind) to static/asimov.tsv.

Each tab's rows are tagged with a Kind column derived from the tab name
via TAB_KIND_MAP. The merged result is written as a single TSV consumed
by the runtime loader and by scripts/generate-site.py.
"""
import csv
import io
import sys
import urllib.parse
import urllib.request
from collections import Counter
from pathlib import Path

SHEET_ID = "1hDNXas7DzwglB95HV2_2u1utWAwBZR2hQHlMPz-fj5A"

# Each tab's name (as it appears in the sheet) maps to a Kind value.
# Speculative tabs use scenario-<slug> kinds; "speculative" is a derived
# predicate (kind.startsWith("scenario-")), not a separate column.
# Iteration order is preserved in the merged TSV, so list legacy first.
TAB_KIND_MAP = {
    "Asimov Prehistory to 1993":   "legacy",
    "Boris additions":             "added",
    "Speculative: AGI-dominant":   "scenario-agi-dominant",
    "Speculative: Fusion economy": "scenario-fusion",
}

OUT = Path(__file__).resolve().parent.parent / "static" / "asimov.tsv"

def fetch_tab(name):
    # gviz/tq accepts ?sheet=<tab-name> so we never need to look up gids.
    # tqx=out:csv returns CSV; we convert to TSV when we write the merged file.
    encoded = urllib.parse.quote(name)
    url = (
        f"https://docs.google.com/spreadsheets/d/{SHEET_ID}/gviz/tq"
        f"?tqx=out:csv&sheet={encoded}"
    )
    print(f"  fetching tab {name!r}")
    with urllib.request.urlopen(url, timeout=30) as resp:
        return resp.read().decode("utf-8")

def main():
    rows_out = []
    header = None
    breakdown = Counter()

    for tab_name, kind in TAB_KIND_MAP.items():
        body = fetch_tab(tab_name)
        reader = csv.DictReader(io.StringIO(body))  # gviz returns CSV
        if header is None:
            header = list(reader.fieldnames or []) + ["Kind"]
        for row in reader:
            if not (row.get("ID") or "").strip():
                continue
            row["Kind"] = kind
            rows_out.append(row)
            breakdown[kind] += 1

    # Write merged TSV. extrasaction='ignore' tolerates a tab that has
    # extra columns we don't care about (notes, scratch fields).
    buf = io.StringIO()
    writer = csv.DictWriter(buf, fieldnames=header, delimiter="\t",
                            extrasaction="ignore", lineterminator="\n")
    writer.writeheader()
    for r in rows_out:
        writer.writerow(r)
    OUT.write_text(buf.getvalue(), encoding="utf-8")

    print(f"wrote {len(rows_out)} rows to {OUT}")
    for k, n in breakdown.most_common():
        print(f"  {k:<28} {n}")

if __name__ == "__main__":
    sys.exit(main())
```

Run with `uv run scripts/fetch-tsv.py` (matches the existing `uv run` convention in `deploy.sh`).

The user only edits the `TAB_KIND_MAP` — no gid lookups, no sheet-side schema changes. Adding a new scenario is one new entry in the map plus a new tab in the sheet.

[deploy.sh](deploy.sh) gains one line:

```sh
#!/usr/bin/env sh
set -e
DEPLOY_DIR=~/Projects/invention.cards/
uv run scripts/fetch-tsv.py            # NEW — sync sheet → TSV before build
uv run scripts/generate-site.py -o $DEPLOY_DIR
…
```

The user can also run the fetch script standalone whenever they edit the sheet, to refresh `static/asimov.tsv` and review the diff before committing.

## Loader changes ([static/utils.js](static/utils.js))

In `loadGraph` (utils.js:103), inside the row-mapping loop:

```js
const FIXED_KINDS = new Set(["legacy", "added"]);
const seenUnknownKinds = new Set();

function normalizeKind(raw) {
  const k = (raw || "").trim() || "legacy";
  if (FIXED_KINDS.has(k) || k.startsWith("scenario-")) return k;
  if (!seenUnknownKinds.has(k)) {
    console.warn(`Unknown Kind value "${k}" — treating as legacy.`);
    seenUnknownKinds.add(k);
  }
  return "legacy";
}

const nodes = rows.map((row) => ({
  id: row.ID,
  year: parseYear(row.Year),
  deps: parseDeps(row.Dependencies),
  title: row.Title,
  description: row.Description,
  inventor: row.Inventor,
  location: row.Location,
  field: row.Field.toLowerCase() || "unknown",
  url: row.URL,
  kind: normalizeKind(row.Kind),
}));

export const isSpeculative = (n) => n.kind.startsWith("scenario-");
export const scenarioOf = (n) =>
  isSpeculative(n) ? n.kind.slice("scenario-".length) : null;
```

In `validateData` (utils.js:36), one new optional check:

```js
const nowYear = new Date().getFullYear();
for (const node of nodes) {
  if (isSpeculative(node) && node.year < nowYear) {
    console.warn(
      `Speculative node ${node.id} (${node.kind}) has year ${node.year} ` +
      `(in the past) — should it be 'added'?`
    );
  }
}
```

Existing rules (duplicate IDs, missing deps, self-reference, future deps, valid fields) are unchanged. Speculative cards with future years and past-card deps are valid.

## Visual treatment

The hierarchy: legacy = neutral; added = subtle accent; any `scenario-…` = clearly different (dashed border, italic title).

**Different scenarios are not visually differentiated in this plan.** All cards with any `scenario-…` kind share the same dashed/italic treatment. The scenario slug is recoverable via `scenarioOf(node)`, ready for a follow-up feature: a scenario picker in the header that filters which scenario(s) are visible (e.g. "show only `scenario-agi-dominant`"), and/or scenario-specific accent colors so two scenarios on screen can be told apart. That UI is out of scope here; this plan ensures the data is loaded so it can be added later without re-touching the pipeline.

Two classes are applied to every rendered element:
- `kind-${node.kind}` — exact value (`kind-legacy`, `kind-added`, `kind-scenario-fusion`, …)
- `is-speculative` — derived bool, set when `node.kind.startsWith("scenario-")`

The `is-speculative` class is the catch-all selector for "any scenario card looks like this." Per-scenario styling can later target `.kind-scenario-<slug>` directly without touching the shared rule.

```css
/* universe.css — appended */

/* `added` cards: thin amber accent. Visible on close inspection; does
   not compete with the existing card chrome. */
g.card.kind-added rect.container {
  stroke: #c89b3c;
  stroke-width: 1.5;
}
.dag-dot.kind-added {
  stroke: #c89b3c;
  stroke-width: 2;
}

/* Any scenario- card: dashed border, italic title, footer "speculative"
   suffix, slightly desaturated. Reads at a glance as "this is a thought
   experiment." Per-scenario differentiation is a future feature. */
g.card.is-speculative rect.container {
  stroke: #6b6b6b;
  stroke-width: 1.5;
  stroke-dasharray: 6 3;
}
g.card.is-speculative .card-title { font-style: italic; }
g.card.is-speculative .card-footer::after { content: " · speculative"; opacity: 0.7; }
.dag-dot.is-speculative {
  fill: white;
  stroke: #6b6b6b;
  stroke-width: 2;
  stroke-dasharray: 2 2;
}
.dag-label.is-speculative .dag-label-text { font-style: italic; }
```

Specific selectors (`.card-title`, `.card-footer::after`) need to match what `card.js` actually emits — to be confirmed during implementation by reading [card.js](static/card.js). If the title element doesn't have a class, this becomes a one-line addition in `renderFullCard` to tag it.

The two classes are applied at three places:
- [card.js renderFullCard](static/card.js) — on the root `g.card` group
- [world.js renderDots](static/world.js) — on each `circle.dag-dot`
- [universe.js appendLabels:693](static/universe.js#L693) — on each `g.dag-label`

```js
sel.classed(`kind-${d.kind}`, true).classed("is-speculative", isSpeculative(d));
```

## Initial-fit layout: exclude speculative from `initialTransform`

[static/world.js layout()](static/world.js) computes `state.bbox` from all nodes. With scenario cards extending into the future, the timeline could grow wide enough that on first paint the historical density (where 99% of cards live) is squashed.

**Change**: `layout()` continues to compute one bbox over all nodes (used by zoom-constrain so the user *can* pan/zoom into scenario content), but **also** computes `state.fitBbox` over only non-speculative nodes (`!isSpeculative(n)`). [universe.js initialTransform()](static/universe.js#L548) uses `fitBbox`. Pan-and-zoom can still reach scenario cards normally.

If `fitBbox` is empty (e.g., user has loaded a corpus with only scenario entries — unlikely), fall back to the full bbox.

## Validation considerations

- The existing `depYear > node.year` check (utils.js:60) handles speculative cards correctly — speculative future cards depending on past cards is the normal case.
- The new "speculative-but-past-year" warning is a soft hint, not an error.
- Field validation (`VALID_FIELDS` in utils.js:25) is unchanged. `kind` is orthogonal to `field`; both coexist.
- No change to `generate-site.py` is strictly required — `load_inventions` doesn't read Kind, and per-card SEO pages can render uniformly across kinds. (Optional follow-up: emit a `<meta name="invention-kind">` so the static pages carry kind info; out of scope here.)

## Verification

End-to-end browser tests with the dev server running, after the sheet has at least one `added` and one `speculative` row:

- Run `uv run scripts/fetch-tsv.py` → `static/asimov.tsv` updates; the diff is the new `Kind` column on existing rows + any new rows; the script prints a breakdown like `legacy 1477 / added 3 / scenario-agi-dominant 2 / scenario-fusion 1`.
- Cold-load `/` → camera fits *up to* the latest non-speculative card; speculative entries are visible only after panning/zooming further right.
- Pan to a `legacy` card → unchanged appearance.
- Pan to an `added` card → soft amber accent on the card border / dot stroke at every tier.
- Pan to any `scenario-…` card → dashed border, italic title, "· speculative" footer suffix at FULL tier; dashed dot stroke at LABEL tier. The card's DOM has both `kind-scenario-fusion` (specific) and `is-speculative` (catch-all) classes (visible in inspector).
- Cards from two different scenarios visible on screen at once look identical (shared `is-speculative` styling; per-scenario differentiation is deferred to a future filter UI).
- Add a row with `Kind = bogus` → one `console.warn`, that row renders as legacy.
- Add a `scenario-future-x` row with year in the past → one `console.warn`, renders normally.
- Search → matches across all kinds; goldenrod highlight overlays the kind treatment without conflict.
- Hover an `added` or `speculative` card → goldenrod hover overlay still fires; kind treatment persists underneath.
- Pin an `added` or `speculative` card → steelblue overlay still fires; URL becomes `/<id>/`; kind treatment persists.
- Re-run the fetch script after editing the sheet → `git diff static/asimov.tsv` shows exactly the rows that changed in the sheet.
- Remove a tab from `TAB_KIND_MAP` temporarily → fetch script skips it; runtime treats remaining rows correctly.
- Run `deploy.sh` (dry-run if possible) → fetch step runs, then generate-site, then push. No new errors.
